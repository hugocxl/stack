P9DS

P9DS is the design system we use across our websites. It brings the writing, drawings, and controls together in one place.

Start with the interface guidelines and type and color. Then read how to build controls, define a design, compose a page, and brief an agent.

Move across the keys to try the keyboard, or use the arrows to explore another figure. Each drawing responds in place, keeping the example close to the writing.

Interface guidelines

Start with what the reader came for. Explain the subject in a few connected sentences, then bring in an example where it answers a question. On a product screen, name the object being edited and keep the action beside it. In an article, a sentence can lead straight into the next thought.

Keep prose within a centered column of up to 60ch. Let illustrations reach the page gutters when the details need more room. Use about a line of space between paragraphs, with a longer pause when the subject changes.

Type and color

Set the page in Geist Sans. Use weight 300 for reading, 400 for controls, and 600 for headings that need emphasis. At 1440 px wide, body text is about 21 px. It scales with the viewport, with a line height of 1.3. Short section labels use the body size. Set commands and technical notes in Geist Mono.

Give the main thought the foreground color. Use the muted tone for context, examples, or a supporting paragraph. Bring the ink forward again when someone needs to make a decision.

Apollo’s dark canvas pairs near-black with soft white. Light mode reverses the paper and ink. Light surfaces use #f2f2f2 with #505050 for muted text. Dark surfaces use #131313 with #808080 for muted text. Ring is the light rule color. Dark rules use #1d1d1d. Apply the theme roles in system/cxl.css and remember the reader’s choice.

Controls and feedback

Use a link to take someone somewhere and a button to perform an action. Keep field labels visible while typing. When an entry needs correction, keep what was typed and explain the fix beside the field. “Enter a date after 18 November” tells the reader exactly what to change.

Use the filled button for the primary action in a group. Use underlined text for supporting links and group related icon controls on one surface, as with the figure arrows above. Give icon controls an accessible name, give controls a 44 px target, and keep keyboard focus visible. Convey selection with a persistent cue and honor reduced motion and reduced transparency preferences.

Account for the whole task. Show progress during a save, prevent duplicate submissions, and announce completion in place. An empty list needs a first action. A failed request needs a way to retry.

Figures and motion

Choose a drawing that explains the subject. A keyboard belongs beside a shortcut list, where the commands can still be selected and copied. Reserve the drawing’s space as the page loads. Describe meaningful imagery, give interactive figures keyboard controls, and provide a usable still view for readers who prefer reduced motion.

Define a design

Start with the task. Name who the page serves, what they came to do, and how they’ll know it worked. The figure picker lets a reader find a named figure, preview it with the keyboard, and confirm the change in the caption. Test the task with representative users. GOV.UK design principles.

Give visual choices a rule. Specify the role, value or formula, and context. A section heading in P9DS uses the reading size, weight 400, and the theme’s muted text color. Define asset paths, proportions, and cropping when the image matters. Pair text colors with their intended backgrounds in each theme. USWDS color roles.

Define a component through its behavior. Record the markup, required content, allowed variants, default, and what changes in each applicable state. An unknown figure name leaves the drawing and search value in place, marks the field invalid, and announces what to try. A valid name updates the drawing and moves focus to the next-figure button. Text input specification and ARIA interaction patterns.

Specify how the same content fits at narrow widths, with long labels, and at increased text size. Keep an accessible reading and focus order. Give every required rule a coded example or a check someone can run. Research with users establishes whether the design serves the task. GOV.UK contribution criteria and Evaluating accessibility.

Page composition

Use this page’s editorial shell for every page type. Set the opening in .cxl-introduction, follow with section headings at body size, and use the same centered reading column. Leave 1.25rem between paragraphs and 2.5rem around sections. A wide figure can extend to the gutters up to 1280px. The textured right margin narrows to a strip at 760px.

Product homepage. Lead with the promise, a short explanation, and one primary action. Show the product in a figure. Follow with two or three workflows, then customer evidence or recent updates when available. End with the primary action and plain footer links.

Feature page. Name the outcome and walk through the steps in order. Pair each step with a short paragraph and a figure or captioned screenshot. Keep the copy ahead of its figure at every width.

Pricing. List plans in order of scope. Give each a name, price with currency and billing period, a short list of what is included, and an action. Separate plans with a fine rule. Use a table with row and column headings when readers need to compare the same attributes.

Changelog and documentation. Lead each release entry with a date in Geist Mono, then a heading and what changed. Keep the newest entry first. For a reference article, put jump links in an opening paragraph and keep examples close to the rules they illustrate.

Contact or signup. Start with the task and place a labeled form directly beneath it. Ask for the information the task needs. Keep validation beside the field, and put submission status and retry by the action.

Hand off a design to an agent

Give the agent a versioned reference and a page brief. Pin a P9DS commit. Explicitly ask it to read DESIGN.md and the relevant markup and CSS. Supply ordered sections, exact copy, local asset paths, action destinations, and fixtures for applicable states. Name any choices the agent can make. Omit optional sections without source content and surface missing required inputs for review.

Use each file for a clear purpose. The Google Labs draft pairs YAML tokens with prose and references to component source. Here, the shared CSS owns the rendered values and DESIGN.md records the tokens and usage. Exchange tokens with other tools using the DTCG JSON format when needed. Download DESIGN.md, Google Labs format, and Design Tokens specification.

Make the build repeatable. Model output can vary with the same prompt and decoding settings. For an automated generator, have the agent propose a page plan as data. Validate the plan against a schema of allowed components and fields, then check section order, asset IDs, and destinations. Save the approved plan and render it with pinned templates and styles. Rebuilding then uses the saved inputs. Research on inference variability and Component catalogs for agents.

Check computed styles, section order, keyboard behavior, and reflow in both themes. For pixel comparison, fix the browser build and OS, viewport, scale, content, state, locale, and motion settings. Wait for the bundled fonts and images before capturing. Visual comparison guide.

Build and review

Copy the system/ folder into your project and load both stylesheets. The fonts, figures, and theme tokens travel together.

<link rel="stylesheet" href="system/cxl.css"> <link rel="stylesheet" href="system/editorial.css">

Set cxl-editorial on the body. Inside main, wrap the article with cxl-reading cxl-opening. Add cxl-wide-figure when an illustration needs the full width. Load system/theme.js in the document head to apply the saved appearance. Browse the source files ↗.

Before shipping, complete the principal task with a keyboard. Check both appearances, reduced motion, long labels, reflow at 320 CSS pixels, and 200% zoom. Follow WCAG 2.2 AA for the finished page.
